# Technical Proof-of-Learning Answers

## Q1 - Certification and exam mechanics

In Andrew Brown's 2024 course video, he reports the exam was delivered through PSI, lasted 120 minutes, and had 75 questions: 60 scored items plus 15 unscored pretest items. He says GitHub did not publish an official passing score; his 75% figure was described as unofficial. He strongly recommends practice exams because some exam-relevant material was not clearly documented, and the practice questions helped learners prepare for the exam's scenario and troubleshooting style. Treat these details as the historical video answer. GitHub's current certification information has changed: the current page lists 60 scored questions plus approximately 10-15 pretest questions, 100 minutes, and Pearson VUE. It does not publish an official passing percentage. [1][2]

## Q2 - Core architectural hierarchy

A workflow is a YAML-defined automation stored under `.github/workflows/`. An event starts it, such as push, pull_request, schedule, workflow_dispatch, or repository_dispatch. A workflow contains jobs; independent jobs run in parallel by default. A job is assigned to a runner and contains ordered steps. A step either runs a shell command or calls an action, which is a reusable unit of automation. Use the `needs` keyword to make a job wait for one or more dependent jobs, for example `needs: build` or `needs: [build, test]`. [3][4]

## Q3 - Event triggers and repository_dispatch

`push` and `pull_request` are repository events generated by activity in the repository. `repository_dispatch` lets an external system request a workflow run through GitHub's REST API. Send an HTTP POST to `https://api.github.com/repos/OWNER/REPO/dispatches` with `Accept: application/vnd.github+json`, `Authorization: Bearer TOKEN`, and `X-GitHub-Api-Version`. The JSON body needs `event_type`, and may include `client_payload`, for example `{"event_type":"custom-webhook","client_payload":{"data":"demo"}}`. A fine-grained PAT needs Contents: write on that repository; a classic PAT requires the repo scope. A successful request returns 204. The workflow must be on the default branch for the event to start it. [5]

## Q4 - Cron syntax and branch constraints

A scheduled trigger is configured under `on.schedule` with a POSIX five-field cron string:

```yaml
on:
  schedule:
    - cron: '*/5 * * * *'
```

The example runs every five minutes, and scheduled times are interpreted as UTC by default. Scheduled workflows only run from the default branch, and the workflow file must exist there. Runs can be delayed under heavy Actions load. [6]

## Q5 - Context objects and expressions

Five built-in contexts include `github` (event, actor, ref, repository), `env` (workflow/job/step environment values), `vars` (configuration variables), `secrets` (encrypted secret values), and `runner` (runner operating system and environment). Other contexts include `job`, `steps`, `strategy`, `matrix`, `needs`, and `inputs`. Expressions use `${{ ... }}` to access contexts and evaluate functions; some fields such as `if:` accept expressions without the wrapper. Common status functions are `success()`, `failure()`, `always()`, and `cancelled()`. GitHub applies an implicit `success()` condition unless a status-check function changes that behavior. [7][8]

## Q6 - Secrets, variables, and GITHUB_TOKEN

Secrets are intended for confidential values such as credentials; GitHub stores them encrypted and masks recognized secret values in logs. Configuration variables (`vars`) are for non-sensitive settings and are not a substitute for secret storage. A workflow should never print a real secret. `GITHUB_TOKEN` is automatically created for each workflow job as a GitHub App installation token, scoped by the workflow's permissions and limited to the repository. It expires when the job ends or when its effective maximum lifetime is reached. Grant only the permissions a workflow needs. [9][10]

## Q7 - GitHub-hosted versus self-hosted runners

GitHub-hosted runners use a fresh GitHub-managed virtual machine for each job; GitHub maintains the image and infrastructure. Usage is subject to the account's plan, included minutes, and runner pricing rules. Network and machine-level control are limited to what GitHub provides. Self-hosted runners use infrastructure maintained by the student or organization, so the owner handles updates, connectivity, capacity, and security. They avoid GitHub-hosted runner-minute charges, but require local hardware or cloud resources and operational maintenance. They offer more control over the machine and network, which also means jobs can access that environment. Do not run public pull-request code on a self-hosted machine; restrict the demonstration job to a trusted manual dispatch. [11][12]

## Q8 - Matrix builds and caching

A matrix strategy expands one job definition into separate runs for combinations of values, such as three operating systems and two Node versions, producing six jobs. Dependency caching stores reusable package files under a key often derived from the operating system and lockfile hash. A cache hit restores the cached files and reduces downloads or install time. On a miss, the job installs dependencies and saves a cache after a successful run; a later run with the same key can restore it. [13]

## Q9 - Service containers

A service container is an ephemeral Docker container attached to a job, commonly used for a database or cache during integration tests. GitHub starts it for the job and removes it after the job finishes. When the job runs directly on the runner machine, the service's port must be mapped and steps connect through `localhost:<port>`. When the job itself runs in a container, it connects to the service by the service label as a hostname. Service and job containers require a Linux runner; on GitHub-hosted runners use Ubuntu, and a self-hosted runner must be Linux with Docker installed. [14]

## Q10 - Custom action types and compilation

The three action types are JavaScript actions, Docker container actions, and composite actions. A JavaScript action declares its metadata and runtime in `action.yml`, with its implementation in JavaScript. `@vercel/ncc` bundles the entry point and its dependencies into `dist/index.js`, a distributable file the runner can execute without a separate `node_modules` installation. The compiled `dist/index.js` must be committed and referenced from `action.yml`; semantic version tags such as `v1.0.0` and `v1` make the action invocable by consumers. [15]
